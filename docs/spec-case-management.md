# 依頼: AI導入補助金 案件管理システムの実装（今あるものに追加する版）

このリポジトリ（it-subsidy-intake）にはすでに、書類提出フォーム・AIによる書類判定・ポータル同期・管理者ログインがあります。今あるものを土台にして足りない部分を追加し、仕様と違うところだけを直してください。
仕様にない判断が必要になったら、勝手に決めずに質問してください。命名やディレクトリ構成など実装上の細かい判断は任せます。

## 1. 背景

- 申請会社「Assemble」が、このシステムを使って顧客企業（申請企業）の補助金申請を代行します。
- 今は「回次＋ツール頭文字×会社名＋様」という名前のグループLINE（例: `３次BU×MEM株式会社様`）に担当者が個人で入り、1つずつ開いて進捗を確認しています。これをなくすことが目的です。

## 2. 今あるもの（そのまま使う）

| 機能 | 場所 | 扱い |
| --- | --- | --- |
| 書類提出フォーム（ログイン不要・推測できないトークン付きURL・gBizIDなどの確認項目） | `app/(public)/apply/[token]` | そのまま使う。**URLの有効期限は付けない**（今のまま） |
| AIによる書類判定（Google VisionでOCR → Claudeで抽出・判定、写真の四隅チェック、会社情報との照合） | `lib/claude/*`, `lib/ocr/*`, `lib/validation/crossCheck.ts` | そのまま使う。判定条件の一部を管理画面で変えられるようにする（5-6） |
| 個人事業主の申請 | `applicant_type = 'sole_proprietor'` | **残す** |
| ポータル同期（このリポジトリ内のPlaywright、Vercel cronで1日1回＋手動ボタン） | `lib/portal/*`, `app/api/cron/portal-sync` | **取得の仕組みは今のまま**。取り込み後の照合・差分・通知を追加する（5-2） |
| 管理者ログイン（パスワード＋署名付きCookie） | `lib/auth/adminSession.ts` | **今のまま**。Supabase Authには移さない |
| 支援事業者の管理・ポータルのログイン情報 | `app/admin/(secure)/vendors` | そのまま使う |
| 担当者向けの共有URL | `app/share/[token]` | そのまま使う |

## 3. 技術構成

今のまま（Next.js 15 App Router・Supabase・Claude API・Vercel）。追加するのは LINE Messaging API（Webhook受信・グループ名の取得・送信）だけです。

## 4. 全体の流れ

1. 社内が案件を登録する（会社情報を入力すると同意書が自動で作られる）
2. 顧客が同意書に電子署名する
3. 顧客が専用フォームから書類を提出する（AIで判定し、不備はその場で表示）← 今ある
4. 書類がそろうと、公式LINEから社内用グループに通知する
5. 社内がグループLINEを作り、公式LINEを招待する（グループ名と会話から自動で案件に紐付く）
6. 社内がポータルで申請する（今の運用のまま）
7. ポータル同期で、申請番号・法人番号を使って案件と照合し、状態を取り込む ← 取得は今ある
8. 採択・交付決定を取り込み、フィーを計算し、社内の段階を自動で更新する
9. 請求・契約・入金をチェック項目で並行して管理する

## 5. データモデル

### 方針

- **案件は今の `applications` 表をそのまま使う**（名前は変えない）。列を追加して案件の情報を持たせる。今あるデータの移し替えが不要で、フォーム・判定・ポータル・共有の今のコードに手を入れずに済むため
- 会社の表（companies）は作らない。会社情報は案件の列として持つ。同じ会社が複数の回次で申請する運用が多くなったら、あとで分ける
- 権限は今の方式のまま: RLSは有効・許可ルールは作らない・読み書きはすべてサーバー側（管理者権限のキー）経由。新しい表もこの方式にそろえる
- 変更はすべて `supabase/migrations/` に新しいファイルとして追加する

### `applications` に追加する列

| 列 | 内容 |
| --- | --- |
| corporate_number | 法人番号（13桁・個人事業主は空） |
| company_name_normalized | 照合用の会社名（`normalizeName` で作る。保存時に更新） |
| representative_name | 代表者 |
| address | 所在地 |
| tool_id | ツール（`tools`） |
| round | 申請回次（整数） |
| staff_account_id | 社内担当（`accounts`） |
| referrer | 紹介元 |
| stage_id | 現在の段階（`stages`） |
| subsidy_amount | 補助金額 |
| fee_estimated | フィー見込み額 |
| fee_confirmed | フィー確定額 |

今ある `portal_application_no` / `portal_status` / `portal_status_updated_on` / `portal_synced_at` は、ポータルの公式の状態として**自動更新専用**にする（画面から手で書き換えられないようにする）。

### 新しく作る表

| 表 | 主な項目 |
| --- | --- |
| tools（ツール） | 頭文字、ツール名、計算方法（rate / fixed）、率または金額、請求タイミング |
| stages（段階） | 名前、並び順、色、ポータル連動ルール、顧客通知の有無（初期値はオフ）、顧客向け定型文 |
| check_item_defs（チェック項目の定義） | 名前、対象の段階、期限日数 |
| case_checks（案件のチェック） | 案件、項目、完了日、完了者 |
| doc_type_settings（書類の判定設定） | 書類の種類（今のenumの値）、表示名、必須かどうか、判定の設定値（5-6）、受け付けるファイル形式 |
| contracts（電子契約） | 案件、状態、署名日時、署名者情報、IPアドレス、締結後PDFのハッシュ値、タイムスタンプ（後から付ける用・空でよい） |
| line_groups（LINEグループ） | グループID、種類（customer / internal）、グループ名、案件、紐付け方法（auto / manual）、名前の最終取得日時 |
| line_send_failures（LINEの送れなかった通知） | 送り先、本文、理由（上限など）、日時、再送済みか |
| billing_schedules（請求予定） | 案件、金額、発生日、請求書発行日、入金日 |
| accounts（社内担当） | 氏名、ロール、メモ。ログインには使わない（担当者の名前を選ぶための表） |
| status_history（変更履歴） | 案件、項目、変更前、変更後、変更者の種類（staff / portal / line）、日時 |

ポータルの取得結果は、今ある `portal_cases`（最新の状態）と `portal_sync_runs`（実行の記録）を使う。前回との差分は `status_history` に記録する。

### 初期データ

- tools: `BU` は補助金額の15%、`LU` は補助金額の10%。請求タイミングはどちらも「補助金の入金後」
- doc_type_settings: 今ある書類の種類すべて（法人・個人事業主の両方）

## 6. 機能仕様

### 6-1 案件台帳

- 今の管理画面の新規作成（`/admin/dashboard/new`）と詳細画面に、案件の項目を追加する: 会社名、法人番号、代表者、所在地、担当者の連絡先、ツール、申請回次、社内担当、紹介元
- 一覧画面（`/admin/dashboard`）に、段階・チェック項目・ポータル状態・回次・次の期限での絞り込みと並べ替えを追加する（今ある絞り込みは残す）
- 既存の案件をCSVで一括登録できるようにする

### 6-2 ポータル同期（取得の仕組みは今のまま）

- 取得の処理（`lib/portal/scraper.ts`・`browser.ts`）と実行回数（1日1回・JST 6時＋手動）は変えない
- 取り込んだ後の案件との照合を、申請番号 → 法人番号 → 正規化した会社名 の順に広げる。会社名で一致したものは候補として出すだけで、確定は人が行う（管理画面の `/admin/portal` に候補の確定ボタンを付ける）
- 前回の取得結果との差分だけを `status_history` に記録し、状態が変わった案件を社内用グループにまとめて通知する（同期1回につき1通）
- 取得に失敗したとき（ログイン失敗・画面構成の変更）は、社内用グループにすぐ通知する

### 6-3 段階とチェック項目

- 段階とチェック項目は、管理画面で自由に追加・並べ替え・削除できるようにする。コードに決め打ちしない
- ポータル連動ルール（例: ポータルが「採択」になったら社内段階をXに進める）を段階に持たせる
- 段階・チェック・補助金額・フィーの変更はすべて `status_history` に残す
- 今の `applications.status`（draft / submitted など）は「書類提出フォームの状態」としてそのまま残し、社内の段階（`stage_id`）とは別に扱う

### 6-4 フィー計算

- 計算方法は「補助金額×率」と「定額」から選べる
- 請求タイミングはツールごとに選ぶ（同意書の締結時・申請完了時・採択時・交付決定時・補助金の入金後）
- 採択の時点で見込み額、交付決定の時点で確定額を計算し、補助金額が変わったら計算し直す
- 案件が請求タイミングに達したら `billing_schedules` に請求予定を作り、チェック項目「請求書発行」を立てる
- ツール別・回次別・月別の売上見込みを一覧で表示する

### 6-5 同意書と電子契約（自前で作る）

- 案件の情報を差し込んで同意書のPDFを作る。当事者は申請企業とAssemble
- 文面は後で差し替えるので、差し込む項目を変数にした仮の文面で作る
- 顧客には推測できないトークン付きの専用URLを送り、内容の確認 → 署名（氏名の入力または手書き）→ 締結 の順で進める。有効期限は付けない（書類提出フォームと同じ）
- 署名日時・IPアドレス・署名者の情報と、締結後のPDFのSHA-256ハッシュ値を保存する。認定タイムスタンプを後から付けられるようにしておく
- 締結が終わったら段階を自動で進め、締結済みのPDFを非公開バケットに保存する

### 6-6 書類の判定（今の仕組みに追加）

- 今の書類ごとの判定処理（`lib/claude/extractors/*`）はそのまま使う。判定の中身はコードのままにして、**数値や選択肢だけ** `doc_type_settings` から読むようにし、管理画面で変えられるようにする
  - 例: 登記簿謄本の「発行から何か月以内か」、納税証明書の「求める種類（その1〜その4）」、必須かどうか
- 判定に自信がない場合は「担当者確認が必要」にする
- **法人の納税証明書は「その3」を求めるように変える**（今は「その1」でないと不備にしている）。初期値を「その3」にし、表示名・顧客向けの説明・不備メッセージもあわせて直す。個人事業主の納税証明書（`tax_cert_2`）は今のまま
- すべてそろって送信されたら、公式LINEから社内用グループに通知する

法人の判定条件（初期値）:

| 書類 | 判定の条件 |
| --- | --- |
| 登記簿謄本（履歴事項全部証明書） | 発行から3か月以内 |
| 納税証明書 | 「その3」であること |
| 決算書 | 損益計算書・貸借対照表・キャッシュフロー計算書がそろい、直近の期であること |
| 写真で提出された書類 | 書類の四隅がすべて写っていること |

あわせて、発行日・法人名・法人番号を読み取り、案件に登録した会社情報と一致しない場合は不備とする（今の `crossCheck.ts` に法人番号の照合を足す）。

### 6-7 公式LINE（新規）

- 招待されたら（join イベント）グループ名を取得し、回次・頭文字・会社名を読み取る。例: `３次BU×MEM株式会社様` → 回次=3、ツール=BU、会社名=MEM株式会社
- 全角半角、「株式会社」の有無、末尾の「様」、空白をそろえてから照合する（今の `normalizeName` に末尾の「様」の除去を足す）
- グループ名だけで1件に絞れない場合は、グループ内の会話に出てくる会社名も使う。それでも1件にならなければ、管理画面で担当者が選ぶ
- グループ名は変更しても通知が来ないので、定期的に取り直して変化を検知する（ポータル同期のcronに相乗りしてよい）
- 社内用グループ（公式LINEと担当者だけ）を `line_groups` の internal として登録し、社内向けの通知はすべてそこへ送る
- 顧客向けの定型文は段階ごとに設定だけしておき、初期状態では送らない（段階ごとに管理画面でオンにできる）
- 参加時の挨拶は、通数を使わない応答メッセージ（replyToken）で返す
- Webhookは署名を検証する

公式LINEは無料プラン（月200通・送信回数×受け取る人数で数える）で使います。push送信は最小限にし、上限で送れなかった通知は `line_send_failures` に残して管理画面に表示してください。

## 7. 進め方

次の順で作り、各フェーズの終わりに動作確認の手順をまとめて報告してから、次に進んでください。

1. フェーズ1: データモデルの追加、案件台帳の項目追加と一覧の絞り込み、ツールとフィー計算、ポータル同期の照合の拡張と差分記録、段階とチェック項目の設定画面、CSV取り込み
2. フェーズ2: 公式LINE（Webhook、自動紐付け、既存グループの取り込み、社内用グループへの通知、ポータル同期の通知）
3. フェーズ3: 同意書の生成と電子契約、書類判定の設定画面と納税証明書「その3」への変更、送信完了の通知
4. フェーズ4: 請求予定の管理と、売上見込みの集計画面

請求書を何で発行するかはまだ決まっていません。フェーズ4では請求予定の管理までを作り、外部連携は差し込める形の入口（インターフェース）だけ用意してください。

## 8. 守ってほしいこと

- 秘密情報（Supabaseのキー、LINEのチャネルシークレットとアクセストークン、Claude APIキー）は環境変数で扱い、`.env.local.example` に項目名だけ追記する
- 今ある機能（フォーム・判定・ポータル取得・共有・支援事業者の管理）を壊さない。各フェーズの終わりに `npm run build` が通ることを確認する
- 主なロジック（グループ名の読み取り、会社名の正規化と照合、フィー計算、ポータルの差分検出）には単体テスト（vitest）を書く
- 各フェーズの終わりに、README に起動手順と動作確認の手順を追記する
